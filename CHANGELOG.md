### Add scheduled folder-watch auto-import + manual "Import Today's Sales" trigger on top of the existing CSV pipeline
- **importPipeline.ts**: New file — `runImport()` finds the first `.csv` in `data/incoming/`, reads it, and calls the real `parseCSV()` from `src/lib/csvParser.ts` unmodified; on success (≥1 parsed entry) moves the file to `data/incoming/processed/<ISO-timestamp>_<name>`, on failure moves it to `data/incoming/failed/<ISO-timestamp>_<name>` and writes a sibling `.log.json` with the row-level `issues`/`errors`; every run persists an `ImportStatus` to `data/incoming/status.json` via `getLastStatus()`; `watchIncoming()` wraps `fs.watch(data/incoming/, ...)` (built-in, no new dependency) with a 300ms settle delay + existence re-check, and a module-level `importInProgress` lock shared with the manual trigger so the watcher and the endpoint can never double-process the same file — why: task requires one shared import function used by both the watcher and the manual endpoint, not two implementations
- **server.ts**: Added `GET /api/import/status` (returns `getLastStatus()`) and `POST /api/import/trigger` (calls `runImport()`; returns `{found:false, message:"No new export found in the watched folder."}` when nothing is queued, else `{found:true, status}`); calls `watchIncoming()` once at startup to arm the folder watch — why: exposes the shared pipeline to the frontend without duplicating its logic
- **src/lib/importClient.ts**: New file — thin fetch wrapper (`getStatus`, `trigger`) matching the two new endpoints' response shapes — why: single place for the frontend's import-API contract, mirrors the existing `authClient.ts`/`aiClient.ts` pattern
- **src/pages/UploadPage.tsx**: Added a "Import Today's Sales" `Button` (same `Button`/`Card` components and dark-theme styling already used on this page — no new visual style) below the existing sample-data buttons; clicking it calls `importClient.trigger()` — on `found:false` shows the required inline message, on success calls `setResult(...)` with the server's parsed entries/issues so the **existing** Preview card and "Save & Continue" button render unchanged (no new preview UI); added a polling `useEffect` (5s) that calls `importClient.getStatus()`, renders `Last auto-import: <time>, <n> rows` near the page header, and — for a folder-watch import the browser hasn't seen yet (tracked via a per-restaurant `biq_auto_import_applied_at_<id>` localStorage flag) — silently applies it via the same `storage.setBilling()` + `buildMenuFromBilling()` calls `saveAndContinue` already uses; the pre-existing drag-and-drop/`processFile`/`saveAndContinue` code path is untouched — why: keeps auto-import (silent, folder-watch) and manual-trigger (explicit preview + confirm) both flowing through the one real commit path, since `storage.ts` is a browser-only `localStorage` module that cannot be called from the Node-side watcher directly
- **.gitignore**: No change needed — `data/` was already ignored from the prior `auth-and-db` branch work, which also covers the new `data/incoming/` folder
- **Design note**: Step 3 of the spec says the file-watcher itself should "call storage.setBilling" — that function reads/writes `localStorage`, which does not exist in the Node server process. Implemented as above instead: the watcher's job ends at parse+file-move+status; the actual `storage.setBilling`/`buildMenuFromBilling` commit happens in the browser (automatically for a watcher-detected import via the polling effect, or after an explicit "Save & Continue" click for a manually-triggered one) — the only place that call can correctly run
