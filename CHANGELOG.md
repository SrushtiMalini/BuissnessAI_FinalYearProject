AND restaurant_id = ?`, which is what makes a targeted single-row mutation tenant-safe too, not just list-level queries). Added two routes beyond the task's literal list, `DELETE /api/billing` and `DELETE /api/reports` — needed so Settings' Danger Zone can still fully clear an account (menu clears via `PUT []`, opportunities via `POST []`, but billing/reports only had an append endpoint otherwise, which would have left Danger Zone unable to actually delete them — a real regression of an already-shipped feature, not a hypothetical)

Reads (`getBilling`, `getMenu`, `getReports`, `getOpportunities`) stay **synchronous** — same signatures every page already calls — backed by an in-memory cache; writes (`appendBilling`, `setMenu`, `appendReport`, `setOpportunities`, `updateOpportunityStatus`, `clearAll`) are now **async** (real network round-trip) and refresh that cache on success. Added `hydrate()` (fetches all four resources in parallel into the cache; must run once after login/signup and once on app boot for an already-authenticated session) and `resetCache()` (called on logout). Added `migrateLegacyLocalData()` — the one-time upgrade path: if this browser still has old client-namespaced `biq_billing_<id>` etc. and the server has nothing yet for this restaurant, push it up once then clear it locally, never touching it again. Restaurant profile, chat, and the other ML-local keys (ingredient mappings, wastage log, pricing recs, promotions) are explicitly out of this task's scope and remain localStorage-only, namespaced exactly as before
- **Consequential change, not explicitly requested but required**: because writes are now async, every call site had to gain `await` — `tsc` only caught one of these (a destructured return-value mismatch); the rest were fire-and-forget promise bugs `tsc` cannot detect on its own, found by manually grepping every call site rather than trusting the compiler: `opportunityEngine.ts`'s `generateOpportunities()` (now itself `async`, awaits `setOpportunities`), and one `await` added each in `UploadPage.tsx` (both the manual save and the auto-import poll path), `DashboardPage.tsx` (`handleOpportunityAction`), `MenuPage.tsx` (`save`), `ml/DynamicPricingPage.tsx` (`applyRecommendation`), `ReportPage.tsx` (`generateReport`, already async), and `SettingsPage.tsx` (`clearAllData`)
- **src/App.tsx**: Added `HydrateGate` — wraps the whole route tree, calls `hydrate()` on mount when a token already exists (page refresh, direct URL nav) and shows a small spinner until it resolves. Without this, a page refresh would zero out the in-memory cache (it's just a JS variable) and every page would flash "no data" until something else happened to re-trigger a fetch — this is what makes "calling pages need zero changes" actually true across refreshes, not just within one continuous session
- **src/pages/LoginPage.tsx, src/pages/SignupPage.tsx**: Added `await hydrate()` right after `authClient.saveSession()`, before navigating away — so the cache is populated by the time the destination page mounts
- **src/layout/AppShell.tsx**: `handleLogout` now also calls `resetCache()` so a subsequent login's `hydrate()` starts from a clean slate rather than serving the previous account's cached data for a frame

### Incident: an early, buggy test run deleted the real "bengaluru cafe" account's billing history from the live dev database — recovered in full
- **What happened**: the first version of `tests/api.test.ts` set `process.env.BIQ_DB_PATH = ':memory:'` **after** a `static` `import { createApp } from '../server.ts'` statement in the same file — but ES module `import` declarations are hoisted above all other top-level code regardless of source order, so `server.ts` (and, transitively, `db.ts`, which opens its DB connection at module-load time) had already connected to the real `data/businessiq.db` before the env var took effect. That test file's `beforeEach` then ran `DELETE FROM billing_entries` against the **real** database, once, before a `FOREIGN KEY` error on the next line (`DELETE FROM restaurants` — wrong table order, also fixed) stopped the run. Net effect: the real account's `billing_entries` table (4,569 rows across 61 distinct dates, per this file's own migration-verification entry above) was wiped; `restaurants` (1 row) and `menu_items` (35 rows) were untouched
- **Fix applied** (see `tests/api.test.ts` entry above): switched to a dynamic `await import('../server.ts')` **after** setting `process.env.BIQ_DB_PATH`, which is a real expression evaluated in place rather than a hoisted declaration — confirmed via a clean re-run that the live DB's row count is unaffected by the test suite (checked before and after `npx vitest run`)
- **Recovery**: froze a raw byte-copy of `businessiq.db`/`-wal`/`-shm` to `data/INCIDENT_BACKUP_20260829_012630/` before any further action. A read-only `grep -a` scan of the `-wal` file for known dish names found hundreds of hits, indicating the pre-delete row data still physically existed in un-checkpointed WAL frames. Parsed the WAL frame format manually (32-byte header, 24-byte-header frames, `dbSizeAfterCommit` marks commit boundaries) on a copy, found the accidental `DELETE`'s ~250-page transaction was the last one in the file, truncated a copy of the WAL to the byte offset of the commit immediately before it, opened `(main db copy + truncated wal copy)` with `better-sqlite3` — SQLite's WAL reader replays a truncated/invalid tail gracefully by design — and confirmed the resulting `billing_entries` table exactly matched the pre-incident state (4,569 rows, 61 distinct dates, same `restaurant_id`). Restored those rows into the live `data/businessiq.db` via an additive `INSERT OR IGNORE` (both counts and a spot-check of `restaurant_id` confirmed correct afterward); `data/recovery_work/attempt/recovered.db` and the `INCIDENT_BACKUP_*` copy were both left on disk (gitignored, not committed) as an audit trail rather than deleted
- **User was informed and made both decisions in real time**: asked before attempting WAL-based recovery at all (vs. treating it as unrecoverable, or having the user handle it independently); asked again, separately, before writing the recovered rows into the live database (that write was also blocked once by Claude Code's own auto-mode safety classifier and required explicit confirmation to proceed)
