### Fix: large-CSV save failure ("Could not reach the server") and blank Dish column in upload preview
- **BUG 1 root cause, confirmed by direct reproduction (not assumed)**: POSTed the real 16,810-row payload (2,447,089 bytes as JSON) to a live `/api/billing` with curl. Server responded `413`, body `PayloadTooLargeError: request entity too large` from `body-parser`/`raw-body`, thrown at `express.json({ limit: "2mb" })` in `server.ts` — the request body (2.33MB) exceeds the configured 2MB cap. The route handler (and its DB transaction) never ran; this is a request-parsing rejection, not a timeout, not a slow row-by-row insert, and not an expired JWT. Ruled out timeout/auth explicitly: `storage.ts` has no `AbortController`/timeout on this call, and `insertBillingEntries` already ran the insert as a single `db.transaction` (not per-row requests) even before this fix.
- **src/lib/storage.ts**: `appendBilling` now splits `newEntries` into 3,000-row chunks and POSTs each to `/api/billing` sequentially, summing `added` and taking the last response's `total` — each chunk (~440KB for typical rows, comfortably under the 2MB server limit even for verbose POS data) instead of one unbounded request. Cache refresh (final `GET /api/billing`) unchanged. An empty array still round-trips once, matching prior behavior.
- **BUG 2 root cause, confirmed by direct DOM/style inspection (not the guessed `dishName`/`dish_name` key mismatch)**: `result.entries[i].dishName` was present and correct at every stage (verified via direct DOM `textContent` query on the live preview table — dish names were always there). The visual "blank" was `getComputedStyle` on the Dish `<td>`: `color: rgb(255,255,255)` (literal `text-white`) against the page's actual background, `getComputedStyle(document.body).backgroundColor` = `rgb(245,242,236)` (`--color-bg-primary: #F5F2EC`, the app's current light "cream" design-system token, set via `src/index.css`). White-on-cream is invisible. `UploadPage.tsx` was never migrated when the rest of the app moved off a hardcoded dark theme onto this CSS-variable design system (`MenuPage.tsx` and `design-system/components/index.tsx` already use `var(--color-text-primary)` etc.) — it still had 5 literal `text-white` occurrences left over from the old dark theme.
- **src/pages/UploadPage.tsx**: Replaced all 5 `text-white` occurrences with `text-[var(--color-text-primary)]` (the design-system token, `#2C2C2C`, correct contrast on the actual `#F5F2EC` background): the Dish column cell (the reported bug), the "Days of data"/"Unique dishes" preview stat numbers (identical invisibility, same root cause, not separately reported but on the same page/table), the "Drop your CSV file here" dropzone label, and the Testing Tools "Generated sales for..." preview line. Left the page's other hardcoded literals (`text-gray-300/400/500`, `bg-[#0D1117]`, `border-[#30363D]`, `text-[#4ADE80]`) untouched — they're merely mismatched-but-visible (borderline-legible gray-on-cream, or a green that reads fine on both), not invisible, and a full theme migration of this page wasn't asked for.

### Fix: session/onboarding kept resetting — root cause was a stale backend process, not the auth or onboarding logic
- **What was reported**: after signing up/logging in once, the app repeatedly bounced the user back to login or the onboarding wizard instead of remembering the session.
- **Root cause, verified directly (not assumed)**: the running `tsx server.ts` dev process had been started *before* same-day edits added a `restaurant_profile` table (`db.ts`) and `GET/PUT /api/restaurant-profile` routes (`server.ts`) that the frontend's onboarding-completion check now depends on. Confirmed by: (1) comparing the live process's start time against `server.ts`/`db.ts` mtimes — the process predated both edits; (2) querying the live SQLite file directly — `restaurant_profile` was absent from `sqlite_master`; (3) reproducing the exact failure with an isolated script that called the real `storage.setRestaurant()`/`hydrate()` against the live (stale) server and observed the `PUT`/`GET /api/restaurant-profile` calls 404, `setRestaurant` return `false`, and `hydrate()`'s `Promise.all` reject.
- **What was ruled out, also verified directly, not assumed**: (a) the 15-minute access-token expiry + auto-refresh-on-401 flow (`fetchWithRefresh` in `storage.ts`) — tested against the (restarted, correct) server with a corrupted access token + valid refresh token: token silently rotated, no redirect to `/login`, request succeeded; separately tested with both tokens invalid: correctly cleared session and redirected to `/login` (intended behavior, not a bug). (b) `RequireOnboarding`'s synchronous cache check in `App.tsx` — tested `setRestaurant()` → simulated reload (`resetCache()` + `hydrate()`) → `getRestaurant()` correctly returned the saved profile once the server had the current schema.
- **Fix 1 (operational)**: restarted the dev server so it loads current `server.ts`/`db.ts` — this alone resolves the reported symptom once the `restaurant_profile` table/routes exist.
- **Fix 2 (`src/lib/storage.ts`, `hydrate()`)**: changed the 5 parallel fetches (billing, menu, reports, opportunities, restaurant-profile) from `Promise.all` to `Promise.allSettled`. `Promise.all` meant a single failing/missing endpoint (exactly what the stale-process condition above produced) silently wiped out **all five** caches — including billing/menu/reports/opportunities, which had nothing to do with the actual failure — leaving the whole app looking broken/un-onboarded rather than just the one affected feature. Verified with a script that simulated only `/api/restaurant-profile` returning 500: before the fix all 5 caches stayed empty; after the fix, billing/menu/reports/opportunities loaded correctly and only the restaurant profile (the genuinely failing one) stayed `null`, logged, and retryable on the next `hydrate()`.
- **Fix 3 (`src/App.tsx`)**: added `RedirectIfOnboarded`, wrapping the `/` route. Previously, visiting `/` — a new tab, a bookmark, or just typing the bare domain — always rendered the onboarding wizard from its empty first step, even for a fully onboarded, authenticated account, since nothing checked completion status for that specific route (only routes *behind* `AppLayout` had `RequireOnboarding`). This independently explains "keeps re-showing the onboarding wizard" as a routing gap, separate from the stale-process issue. Now `/` redirects an already-onboarded session straight to `/dashboard`.

### Harden auth against abuse: rate limiting, refresh-token rotation, and a CI pipeline
- **package.json**: Added `express-rate-limit@8.7.0`.
- **db.ts**: Added `refresh_tokens` table (`id`, `restaurant_id` FK, `token_hash`, `created_at`, `expires_at`, `revoked_at` nullable) + `RefreshTokenRow` interface + indexes on `restaurant_id` and `token_hash`. Only the SHA-256 hash of a refresh token is ever stored — a DB export can't be replayed as a live session.
- **server.ts — rate limiting**: `createApp()` now takes an optional `CreateAppOptions` (`rateLimit`, `authLimiterMax/WindowMs`, `apiLimiterMax/WindowMs`; all default to the production values below, so `startServer()`'s real call site is unaffected). One `authLimiter` (5 attempts / 15 min per IP, `standardHeaders: true` for `RateLimit-*`, JSON body `{error: "Too many attempts, please try again in a few minutes"}`) is applied as middleware to **both** `POST /api/auth/signup` and `POST /api/auth/login` — a shared budget, not one each, so switching endpoints doesn't double an attacker's guessing budget. A separate, looser `app.use("/api", ...)` limiter (100 req/min per IP) covers every other `/api/*` route as general abuse protection, layered on top of (not replacing) the auth limiter on the auth routes themselves.
- **server.ts — refresh token rotation**: Replaced the flat 30-day JWT with a short-lived (15m) access JWT (`signAccessToken`, same `requireAuth` verification as before) plus an opaque, DB-backed refresh token (`issueRefreshToken` — 48 random bytes, 30-day expiry, hashed with SHA-256 via `hashToken` before storage). `/api/auth/signup` and `/api/auth/login` now return `{accessToken, refreshToken, ...}` instead of `{token, ...}`. Added `POST /api/auth/refresh` (validates the presented token isn't expired/revoked, then **revokes it and issues a brand-new pair in the same request** — true rotation, so a reused/leaked old token is rejected, not silently accepted) and `POST /api/auth/logout` (revokes one refresh token by hash; not behind `requireAuth`, since the access token may already be expired by the time a user clicks Logout and revocation only needs the refresh token itself).
